# 饲料供应链经营分析 Agent · 说明报告

> 面向业务读者与面试官。技术细节与运行方式见项目根目录 `README.md`。
> 本项目基于同一作品集的 P1（原料采购成本监测）、P2（NIR 近红外快检）、
> P3（旺季生产-库存-配送协同）三个项目的数据与业务背景构建。

## 1. 这个 Agent 解决什么问题

经营分析的日常痛点不是"没有数据"，而是三句话：

1. **口径不统一**——"库存周转天数"可以是原料/成品、数量/金额、日均/期初期末平均，
   不同口径算出来差 13 倍（本数据集实测：原料口径月均约 1.0 天，成品金额口径月均约 13.4 天）。
2. **数字不可追溯**——报表里的数不知道是哪条 SQL、哪个口径算出来的。
3. **问数门槛高**——业务人员不会 SQL，分析师疲于应付临时取数。

这个 Agent 的做法：**大模型只负责理解问题、选择工具、撰写解读；
所有数字由确定性工具计算；SQL 由语义层（YAML 指标卡）拼接，大模型一个字都不写；
回答中的每个数字都要通过程序化的溯源检查，对不上就报警。**

## 2. 演示四连问（实际运行输出摘录）

### 第 1 问：归因 —— "8月成都厂草鱼料的吨原料成本为什么比7月涨了？"

> 草鱼料（成都厂）2025-07 → 2025-08：吨原料成本 2590.3 → 2714.7 元/吨（+124.3 元）
> 分解：价格效应 **-12.11** 元，配方效应 +0.0 元，出成率效应 **+136.43** 元（三者和恒等于总变化）
> 最大贡献：出成率效应
> 下钻出成率：2025-07月 95.82%，2025-08月 **91.00%**
> 当月质检水分最高原料：玉米 平均水分 15.38%（提示：水分偏高会降低出成率）

Agent 先确认涨了多少，再用连环替代法把涨幅拆成价格/配方/出成率三项效应，
发现主因不是涨价（价格效应反而是负的）而是出成率下滑，再下钻到当月原料质检水分。
每个数字可展开查看对应 SQL。

### 第 2 问：what-if —— "如果豆粕下个月再涨10%，草鱼料配方该怎么调？"

> 【建议，需配方师确认】草鱼料在 2025-12 价格基础上叠加假设 {'豆粕': 0.1}：
> - 新配方吨成本 **2443.3** 元/吨，较基准 2419.1 元/吨变化 **+24.2** 元/吨
> - 新配方：豆粕 8.45%（下调）、菜粕 35%（上调至上限）、棉粕 20%（上限）……
> - 紧约束影子价格：蛋白下限 14.98 元/吨/百分点，赖氨酸下限 126.97 元/吨/百分点

线性规划求解器给出新配方、成本变化、哪些营养约束是紧的（影子价格）。
输出一律标注"建议，需配方师确认"。

### 第 3 问：口径治理 —— "库存周转天数是多少？"

> 这个指标有多个口径，需要先确认：请确认口径：算原料还是成品？按数量还是金额？
> 平均库存用日均还是期初期末平均？
> 可选口径变体：raw_qty_daily（原料·数量·日均库存口径）；fg_amt_avg（成品·金额·期初期末平均口径）

Agent **不直接回答**，而是反问口径。这一步当场展示口径治理的意义——
两个口径在本数据上相差约 13 倍，不澄清就给数是"错一半"。

### 第 4 步：评测页 —— /eval 展示 v0.1→v0.3 的准确率变化与失败分类（见第 4 节）

## 3. 数据与埋点

虚构饲料公司：3 工厂 × 4 产品 × 8 原料 × 6 供应商 × 约 200 客户 × 24 个月
（2024-01 ~ 2025-12），11 张表存于 DuckDB 单文件。
原料采购价锚定 P1 项目抓取的**真实期货行情**（豆粕/菜粕/玉米主力月均价）加随机基差；
配方每月按当月价格用 LP 重算，随价格波动。

数据中埋了 6 个已知问题作为归因题的标准答案（`data/buried_problems.json`）：
出成率异常、供应商蛋白偏低、区域回款恶化、价格高点集中采购、旺季 OTIF 骤降、
原料全年最高价。**真实数据没有标准答案，模拟数据有——这是做量化评测的前提。**

## 4. 评测与迭代（本 Demo 最有说服力的部分）

30 道标准题：单指标查询 10 / 下钻环比 8 / 归因 5 / what-if 4 / 应澄清或拒答 3。
评测指标：数值正确率（±0.5% 容差）、根因命中率、澄清正确性、数字幻觉率（溯源通过率）、
耗时与工具调用数。逐题回答原文留档于 `eval/results_v*.json`，可复核。

| 版本 | 准确率 | 数字溯源通过率 | 平均工具调用 | 平均耗时 | 失败案例与分类 |
|---|---|---|---|---|---|
| v0.1 | 29/30 (96.7%) | 100% | 1.13 | 0.04s | Q06：时间解析错（"2025年7到9月"只识别了7月） |
| v0.2 | 30/30 (100%) | 100% | 1.13 | 0.03s | —— |
| v0.3 | 30/30 (100%) | 100% | 1.13 | 0.03s | ——（另修单位显示缺陷 2 处） |

迭代方法严格按"每轮只改一处、改完全量重跑、结果记入 CHANGELOG"执行。
失败分类框架：口径错 / 维度错 / 时间错 / 工具选错 / 数字幻觉 / 该问没问。

**诚实声明**：offline 模式是确定性规则路由，100% 说明题库被路由规则覆盖，
不代表泛化能力。真实泛化能力以 LLM 模式（config.yaml 配置 API key 后，
同一套评测脚本）的分数为准。基线A（把原始表结构给大模型直接写 SQL）对照实验
同样待 key 配置后运行——**数字必须自己跑出来，留空不编造。**

## 5. 护栏设计

| 护栏 | 实现方式 |
|---|---|
| 数据库只读 | DuckDB read_only 连接 |
| SQL 安全 | 禁写关键字（DROP/DELETE/INSERT…）、LIMIT 500、JSONL 日志 |
| 数字溯源 | 从最终回答提取全部数字，与本轮工具输出逐一比对（容差 0.5%），对不上即标记 |
| 口径治理 | 多口径指标在语义层标记 needs_clarification，强制先澄清 |
| 能力边界 | 指标目录外的问题（毛利率、净利润预测）明确拒答并说明缺什么数据 |
| 专业边界 | 配方/采购类输出一律标注"建议，需配方师确认" |

溯源护栏在开发期真实抓到过 3 次问题：日期被误识别为数字、供应商编号 S03 误识别、
派生均值（上下半年平均）未登记进溯源池——均已修复并回归验证。

## 6. 简易 RAG

`search_docs` 工具用 TF-IDF 字符 n-gram（中文免分词）检索作品集的
报告、指标字典、假设登记表，把既有分析结论作为佐证附在回答后
（例如 OTIF 归因时引用 P3 旺季运力分析的原文片段）。
语料可随作品集文档更新自动扩充，无需向量库等额外组件。

## 7. 局限与后续

1. offline 路由覆盖有限，LLM 模式待真实 key 验证泛化；
2. 连环替代法受替代顺序影响，顺序无关的 Shapley 分解是已知的改进方向；
3. 数据为模拟数据，接入真实 ERP/MES 数据后需重新做数据质量核查与埋点回归；
4. 界面为零依赖 stdlib 实现，功能上不等同于完整 BI，但演示足够且部署零门槛。
